## D1. QQ 入站指令（M3.4）是否需要常驻进程

**状态**：✅ 已决定（2026-11-15）：**方案 A（自实现官方 WebSocket 客户端）+ 常驻形态 A（`station serve`，由使用者的 launchd 托管）**
**记录时间**：2026-11-15
**相关文档**：[CONNECTORS.md](CONNECTORS.md) 第 5 节

### 背景

M3.1–M3.3 已完成配置校验、bark 出站、QQ 出站。剩下的入站指令（`/status`、`/backup status`、`/help`）需要**长期在线的 WebSocket 连接**，而当前工具的形态是"一次性 CLI 调用"。

### 为什么不现在决定

这不是实现细节，而是产品形态选择：一旦引入常驻进程，就要决定它的生命周期、日志、重启策略、崩溃恢复、升级时的行为，以及"它挂了谁发现"。这些都会反过来约束 M4（Agent 执行）的设计。

### 候选方案

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. `station serve` 子命令** | 前台可运行，由使用者的 launchd/systemd 托管 | 工具要自己处理重连、心跳、优雅退出；使用者要自己写服务定义 |
| **B. 工具自己注册系统服务** | `station service install` 写入 launchd plist | 越过"apply 不启动服务"的既有边界，需要单独的权限与确认流程 |
| **C. 完全不做入站** | 只保留出站推送，指令走本机 CLI | 失去"手机上问一句就能查状态"的核心价值 |
| **D. 交给现有 MQ/机器人框架** | 把入站委托给外部程序，本工具只提供查询接口 | 增加外部依赖；但能复用成熟的重连与鉴权 |

### 结论（2026-11-15）

选择 **A + A**：

- 传输：自己实现官方 WebSocket 网关客户端（`src/ws.js` + `src/connectors/qq-gateway.js`），零运行时依赖，不引入 Python SDK 或第三方机器人框架；
- 进程：`station serve` 前台运行，生命周期交给使用者自己的 launchd，工具**不**自动注册系统服务；
- 指令面严格只读：`/status`、`/backup status`、`/help`；写操作仍走 `station worktree` 的受控入口；
- 回复走**被动回复**（带入站 `msg_id`，C2C 最多 4 条、群最多 5 条）；
- 未在 `allowFrom` 里的 openid 一律静默忽略，不回复、不提示。

默认仍是关闭：`notifications.inbound.enabled` 默认 `false`。

### 判断时建议先回答

1. 指令面是否要严格只读？（写操作应留给 M4 的受控任务入口）
2. 常驻进程的生命周期归谁：本工具、使用者、还是系统服务管理器？
3. 断线期间的消息如何处理：丢弃、补拉、还是只保留最后一次状态查询？

## D2. Tailscale 发布哪些端口

**状态**：⏸ 由使用者配置，工具不预设
**记录时间**：2026-11-15

`station expose` 只发布 `remoteAccess.ports` 里明确列出的端口；该数组默认为空，因此**默认不发布任何端口**。工具不猜测哪些服务"应该"对外，也不提供默认端口清单。

判断时建议先回答：哪些服务是"自己设备访问"、哪些是"完全本机"；发布前是否需要在服务侧加鉴权。

## D3. 备份是否包含用户项目数据

**状态**：⚙ 已定默认，但可调整
**记录时间**：2026-11-15

`storage.backup.include` 默认只含 `.station/` 与 `station.json`，**不碰用户项目目录**。要备项目数据必须显式加路径。

判断时建议先回答：默认值是否应该更"保护隐私"（永不自动加项目路径），还是要提供一个 `station backup --include <path>` 的一次性参数。
