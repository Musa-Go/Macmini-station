# Agent 任务设计（M4）

本文是 **M4 的契约**。M4.1 只实现"隔离工作区 + 任务记录"，**不调用任何模型、不修改任何代码**。真正让 Agent 改代码是 M4.3，必须在那之前把这里的闸门全部落地。

---

## 1. 为什么这件事必须最慢

M1–M3 的所有功能都是"读"或"往外发消息"：错了可以重来，最坏是没发出去。

M4 会让一个模型**真的动文件**。一旦出错，后果是代码被改坏、密钥被读走、或者未审核的提交进入主干。所以这里的设计原则和前面不同：**默认关闭、逐级放开、每级都有可验证的失败方式**。

---

## 2. 分级

| 级别 | 能力 | 状态 |
|---|---|---|
| **M4.1** | 创建/列出/移除隔离工作区；记录任务元数据（repo、基线 commit、分支、时间） | 本轮实现 |
| **M4.2** ✅ | 在隔离工作区里跑**受控命令**（`agent.tasks` 白名单），产出结构化结果 | 已合并 |
| **M4.3** ✅ | 让 Agent 在工作区内改代码：工具只负责"在正确位置、用正确权限、启动你配置的 agent 命令" | 已合并 |
| **M4.4** ✅ | 通过测试后提交、推分支、开 **Draft PR**（从不合并） | 已合并 |

**M4.1 不包含任何执行能力**：它只准备一个可以安全执行的地方。

---

## 3. 隔离模型

```
repo/                      使用者的真实工作区（不动）
.station/worktrees/<job>/  每个任务的独立工作树
  └─ 分支 station/job-<id>
.station/jobs/<job>.json   任务元数据（不含任何代码内容）
```

规则：

1. **每个任务一个 worktree + 一个分支**，互不干扰；同一 repo 可并存多个。
2. **基线固定**：记录创建时的 `HEAD` commit；任务的所有改动都相对它可追溯。
3. **源仓库必须干净**：树里有未提交改动时拒绝创建——否则"基线"说不清是什么。
4. **worktree 建在 `.station/` 下**，已被 `.gitignore` 忽略，不会污染仓库。
5. **移除要显式**：有未提交改动时拒绝移除（除非 `--force`），避免默默丢工作。

---

## 4. 预算与门槛（M4.2/M4.3 的前置约定）

| 约束 | 建议默认 | 为什么 |
|---|---|---|
| 单任务最大轮次 | 3 | 防止"改坏了再改回去"的死循环 |
| 单任务超时 | 30 分钟 | 长任务应该有专门设计，不该是默认 |
| 单任务 Token 上限 | 由配置给出，0 表示不限 | 限流应该显式，不能靠"模型自己注意" |
| 测试门槛 | 配置 `agent.gate.task` 后，必须有一次针对**当前内容指纹**的通过记录才允许提交 | "模型说完成了"不是证据；旧结果也不算数 |
| 命令来源 | 只认 `agent.tasks` 里登记的 argv | 不让模型自己决定跑什么 |
| 环境 | 只传 `PATH`/`HOME`/`LANG`（+`TERM`） | 父进程里的 API key 不会漏进任务 |
| 推送目标 | 只允许 `station/job-*` 分支 | 任何路径都不允许直接推 `main` |
| PR 形态 | Draft only | 人工转正并合并 |

---

## 4.1 编排，不重写 agent

M4.3 刻意**不实现 agent 循环**。工具只做三件事：把工作区准备好、把 `agent.command` 里面的 `{prompt}`/`{worktree}` 替换好、把退出码与日志记下来。真正的"读文件—改—跑测试—再改"循环由你配置的 agent（例如 DSH headless）负责。

理由：再写一个 agent 循环就是再造一个 AI 客户端，维护成本与风险都比"编排现有工具"高得多。

## 4.2 CI 由使用者落地（M5）

工具不往你的项目里写 `.github/workflows/`。理由很直接：改 CI 配置等于改**发布链路**，是风险最高的位置之一。M5 只在 `templates/` 里给可复制的模板，落地由人一次手动完成。

`station worktree pr` 只负责开 Draft PR；PR 上的检查来自你自己项目的 workflow。

## 4.3 记录是不可信输入

job 记录是本地可编辑文件，所以它被当作**不可信输入**处理：`assertTrustedJob` 会重新从磁盘读记录、核对路径必须是 `.station/worktrees/<id>`、分支必须由 job id 派生、该路径必须是 git 已登记的 worktree、且当前检出的分支与记录一致。任何一项对不上就拒绝，而不是"相信记录"。

同样的思路适用于 journal：`apply` 的 journal 带 HMAC，回滚前校验；文件条目必须带记录时的哈希，路径必须落在 `.station/` 或备份目标内。

**这能挡住"改成指向 main"和"伪造一个 journal"这类错误与事故，但挡不住已经拿到你用户权限的攻击者**——那种情况下对方能直接改 git 和文件，任何同进程内的防护都无效。

## 4.4 没有操作系统级沙箱

任务与 agent 以你的用户身份执行，worktree 只隔离**git 历史**，不隔离文件系统与网络。设计上不宣称机器级安全；需要强隔离时应把它们放进独立账号或虚拟机。

## 5. 明确不做（M4.1–M4.4 都不做）

- 不自动合并、不自动发布
- 不读取使用者仓库之外的路径
- 不把仓库里的任何文件内容发给模型之外的第三方
- 不在 worktree 里放凭据（密钥只经环境变量/钥匙串，且 M4.3 需要单独评审）
- 不根据"模型认为通过"放行；只认测试命令的退出码

---

## 6. 验收标准（M4.1）

```bash
station worktree create --repo ~/code/project --branch my-fix
# → .station/worktrees/<id> 存在，位于 station/job-<id> 分支，HEAD == 记录的 baseline
station worktree list
# → 列出 id / repo / branch / baseline / created
station worktree remove <id>
# → 目录与分支被清理；有未提交改动时拒绝（除非 --force）
```

失败必须明确：仓库不干净、不是 git 仓库、分支已存在、worktree 路径已占用，都要给出可读原因而不是半途而废。
